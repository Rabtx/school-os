**School OS** is the ultimate operating system for schools in Pakistan and similar networks — built
for **owners, principals, admins, teachers, parents, and students**. It runs most operations on
its own, asks humans only where judgment matters, and lets anyone take control at any time.

> **Canonical presentation.** One page, full product + engineering plan. Detail lives in
> [Product Vision](/docs/product-vision), [Production Roadmap](/docs/production-roadmap), and
> [Product System Design](/docs/product-system-design).

## Slide 1 — What we are building

| School OS **is** | School OS **is not** |
| --- | --- |
| A **smart school operating system** — detects, drafts, notifies, escalates | Another **digital register** where humans type everything |
| **WhatsApp-native** trust engine for parents | Email-first ERP nobody opens |
| **Human-in-the-loop** — AI proposes, people approve | Autonomous AI changing grades or sending sensitive messages alone |
| **Modular monolith** that grows module by module | Microservices day one |
| Built for **AKES-scale Pakistani networks** (200–2K students/campus) | Generic global template |

**Reference network:** Aga Khan Schools (AKES) — Karachi, Lahore, Islamabad — multi-campus,
consent-heavy, audit-ready.

## Slide 2 — The smart system principle

Traditional school software:

```text
Human enters data → system stores data → human checks dashboard → human acts
```

**School OS:**

```text
System observes school state → detects gaps and risk → drafts the next action
→ policy checks what is allowed → human approves OR overrides → system executes
→ audit log records everything
```

### Human vs machine — default rules

| Action | Default | Human |
| --- | --- | --- |
| Mark present from teacher roster | **Auto** after teacher tap | Teacher confirms / overrides |
| WhatsApp arrival alert | **Auto** after present mark | Principal can pause campus alerts |
| Sick report from parent | **Auto** excused absent | Teacher flags mismatch if child arrives |
| Unreachable guardian | **Auto** waterfall + create call task | Admin updates number, re-verify |
| Fee reminder before due date | **Auto** draft + send utility template | Admin edits template / skips case |
| Report card comment | **AI draft** | Teacher **must** approve before publish |
| Grade change | **Never auto** | Teacher + audit trail |
| Expel / sensitive message | **Never auto** | Principal step-up auth |

**Design rule:** If a human would feel blindsided, require approval or offer one-tap override.

## Slide 5 — Tenant architecture (valid from day one)

A tenant is the **school organization** — mission, rules, branding, campuses — not just a
`tenant_id` column.

  title="Multi-campus tenant hierarchy"

  T --> C2[Campus Lahore]
  T --> C3[Campus Islamabad]
  C1 --> Y1[Academic year 2026-27]
  Y1 --> CL[Classes and sections]
  CL --> ST[Students and guardians]
  T --> TS[tenant_settings quiet hours grace windows alert policy]
  T --> TB[tenant_branding white label later]
`}
/>

### Tenant core (Wave 0 — before features)

| Entity | Purpose |
| --- | --- |
| `tenants` | Legal name, slug, **mission**, logo, status, timezone `Asia/Karachi` |
| `tenant_branding` | Colors, Urdu/English display name |
| `tenant_settings` | Academic calendar, grace windows, quiet hours, communication policy |
| `campuses` | Physical sites under tenant |
| `tenant_memberships` | User ↔ tenant ↔ role |
| `roles` | `owner`, `principal`, `admin`, `teacher`, `parent`, `student` |

### Isolation (non-negotiable)

- Every business row: `tenant_id` (+ `campus_id` where relevant)
- Repository layer enforces scope — ignore client-supplied tenant
- Postgres **RLS** on students, guardians, attendance, fees before pilot
- Cross-tenant ID → **404**, not 403
- Platform ops role separate, fully audited

## Slide 6 — Smart attendance (not a guard app)

**Problem with gate-only scanning:** extra app, extra staff, bottleneck, training cost.

**School OS approach:** attendance is **fast, reliable, teacher-owned**, with optional hardware.

| Method | Who | Speed | When |
| --- | --- | --- | --- |
| **Class roster tap** | Teacher mobile | ~2 min/class | **Default daily** |
| **Batch QR scan** | Teacher phone | ~5 sec/student | Large classes, first period |
| **NFC student card** | Shared tablet at door | ~1 sec/tap | Phase 1.5 if school has ID cards |
| **Parent pre-report** | Parent app | Before school | Sick, leave, travel |
| **Auto absent + smart follow-up** | System | After grace window | No mark, no pre-report |
| **Admin kiosk mode** | Web tablet optional | Gate rush | Same codebase, no guard persona |

| Technology | Role |
| --- | --- |
| **QR** (signed rotating token on student ID) | MVP default — every phone, printable cards |
| **NFC** | Add when cards exist — fastest tap |
| **Face recognition** | Off by default — legal/consent heavy |

## Slide 7 — Real-world edge cases (built in, not bolted on)

### Guardian contact graph

Each student has:

- **Primary guardian** (alerts first)
- **Secondary guardian(s)** (fallback)
- **Emergency contact** (voice escalation)
- Per-channel: WhatsApp, SMS, email, push
- **Reachability:** `verified` · `unverified` · `bounced` · `opted_out` · `invalid_number`

### Notification waterfall (unreachable number)

<Mermaid
  title="Smart delivery — never silently fail"
  chart={`
flowchart TD
  Start[Attendance marked present] --> WA1[WhatsApp primary guardian]
  WA1 -->|delivered| Done[Log success show on parent feed]
  WA1 -->|failed| WA2[WhatsApp secondary guardian]
  WA2 -->|failed| SMS[SMS if valid number]
  SMS -->|failed| Email[Email plus push parent app]
  Email -->|failed| Task[Create admin task Call guardian]
  Task --> Dash[Principal dashboard Unreachable 4]
`}
/>

### Sick child (parent-initiated)

```text
Parent app before 7 AM → Sick + optional note
→ System marks EXCUSED absent (no panic alert)
→ Teacher roster shows excused sick reported 7:02
→ If child still arrives → teacher override + audit
```

### True absent (smart, not dumb register)

```text
Grace window e.g. 8:45 AM still unmarked
→ unverified absent
→ WhatsApp Reply 1 if sick 2 if late
→ no reply → auto task for class teacher
→ principal sees follow-up queue not raw spreadsheet
```

### Other policies (tenant-configurable)

- Quiet hours (safety can override)
- Split custody: notify all vs primary only vs fail-over
- OTP verify on opt-in before first message
- Max non-critical alerts per child per day

## Slide 8 — Web dashboards (role-specific)

One login, **different worlds** — not one dashboard with hidden menus.

### Owner dashboard

- Multi-campus **trust score** (attendance + delivery health)
- Revenue: fees collected vs due
- Admissions funnel across network
- Consent % and unreachable guardian roll-up
- AI risk summary (later wave)

### Principal dashboard

- **Live pulse:** present · absent · excused · late · unreachable
- Class drill-down and staff view (later)
- Incident feed: sick reports, failed alerts, overrides
- One-click export for board / AKES network reviews

### Admin dashboard

- Student records, enroll, promote, transfer
- Guardian contact health (invalid numbers, pending verify)
- Fee status, documents vault
- User provisioning (teachers, roles)

### Teacher web (secondary to mobile)

- Lesson planning, gradebook, homework builder
- Test papers and mark entry
- Report comments — **AI draft → teacher approve**
- Class analytics

### Wave 0 — Foundation (weeks 1–4)

**Ship:** Tenant + mission + campuses + settings + RBAC + policy tables
**Exit:** Create school, campuses, users, roles; isolation tests pass

### Wave 1 — Trust loop (weeks 5–12) — **Product Milestone 1**

| Module | Smart behavior |
| --- | --- |
| Attendance | Teacher roster, batch QR, excused/sick pre-report, auto absent follow-up |
| Guardians | Primary/secondary, consent, reachability state |

| Principal web | Live dashboard, unreachable list, override controls |
| Parent mobile | Feed, sick report, verify number |
| Teacher mobile | Roster attendance primary UX |

**Done when:** scan/tap → WhatsApp &lt; 5s p95 · sick suppresses alert · unreachable creates task · zero cross-tenant leak

### Wave 2 — Communication & records (months 4–6)

Announcements · teacher–parent messaging (no personal numbers) · student admin · admissions CRM · optional NFC

### Wave 3 — Academics (months 7–10)

Timetable · teacher planning · homework & assignments · tests & papers · gradebook · report cards

### Wave 4 — Finance (months 11–14)

Fee plans · invoices · Stripe / Razorpay / Paymob / JazzCash · WhatsApp due reminders · receipts

### Wave 5 — Intelligence (months 15–18)

Early warning (attendance + grades + fees) · AI report comments (approve only) · principal briefings · parent FAQ bot (tenant RAG, escalate to human)

### Wave 6 — Scale (year 2+)

Bus + GPS · white-label · enterprise residency · split notifications/AI if load demands

## Slide 11 — Data model spine

Everything plugs into one Postgres source of truth:

```text
tenants → campuses → academic_years → classes → sections
students ↔ student_guardians ↔ guardians
users ↔ tenant_memberships ↔ roles
attendance_sessions → attendance_marks (present|absent|excused|late)
attendance_events → notification_outbox → notification_attempts
guardian_consents · tenant_communication_policies
tasks (call parent · verify document · follow up absent)
audit_logs
```
